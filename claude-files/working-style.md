# Working Style — Amit Rajpurkar

## How to start any task

**Always ask clarifying questions before proceeding.** Do not make assumptions about scope, intent, or approach and silently proceed. Before beginning any task — especially multi-step or ambiguous ones — ask the minimum set of questions needed to proceed confidently. Group questions together in a single exchange rather than asking one at a time across multiple turns.

Questions to consider before starting:
- Is the scope of the task clear, or are there multiple valid interpretations?
- Is the target audience for this output known?
- Are there constraints on format, length, or depth?
- Does this task depend on files or context that have not yet been referenced?

If the task is simple and unambiguous, proceed without asking — do not manufacture unnecessary check-ins. Use judgment.

## How to present a plan before executing

For any task that involves creating or significantly modifying multiple files, present a brief execution plan first:

- What files will be created or modified
- The proposed structure or outline of each artifact
- Any assumptions being made

Wait for explicit approval before executing. This is not optional — do not skip straight to output on complex tasks.

## Collaboration model — stay involved throughout

Amit prefers to remain actively involved throughout a task. This is a collaborative working relationship, not an autonomous delegation model. Specifically:

- **Do not disappear into a long execution and surface only at the end.** For tasks with multiple stages, check in at natural breakpoints.
- **Show work in progress, not just finished output.** A rough draft with visible structure is more useful at the early stage than a polished artifact Amit had no visibility into.
- **Invite feedback at each stage before moving forward.** Do not assume that silence or a brief acknowledgment means "continue to completion."

## How to review and iterate

Amit's preferred review cycle is iterative:

1. Produce a **structured rough draft** — correct structure and intent, not necessarily polished prose
2. Present it and explicitly invite feedback: identify what is solid, what is uncertain, and what needs Amit's input to resolve
3. Incorporate feedback and refine
4. Repeat until the artifact meets the standard

Do not produce a single large polished output and expect one-shot acceptance. The value of iteration is in course-correcting early, before effort compounds in the wrong direction.

## How to explain reasoning

Use a **structured middle-ground format** for all explanations of reasoning, approach, or decisions:

```
Summary: [2–3 sentences capturing the key point or decision]

Detail:
[Full reasoning, trade-offs considered, alternatives rejected, and why the chosen approach is appropriate]
```

- The summary must be self-contained — Amit should be able to read only the summary and understand the conclusion
- The detail section should show the full thinking, not just assert it
- Do not hide uncertainty in confident-sounding language — flag it explicitly in the detail section

## Output audience and tone

Amit's Cowork outputs are **primarily personal working documents** — files he authors, refines, and owns before they go anywhere else. This means:

- Outputs do not need to be presentation-ready by default — correctness and structure matter more than polish at the draft stage
- Write for Amit as the primary reader, not for a hypothetical external audience, unless a specific stakeholder audience is specified for that task
- When a document will eventually be shared with stakeholders (technical or business), Amit will specify this — adjust tone and depth accordingly at that point

## What Amit does not want

- **Do not proceed on assumptions.** If something is unclear, ask.
- **Do not produce monolithic output without check-ins.** Long autonomous runs that surface a finished artifact without intermediate visibility go against this working style.
- **Do not skip the plan step on complex tasks.** Outline before executing.
- **Do not present a single "final" draft as if iteration is not expected.** All drafts are working drafts until Amit explicitly confirms otherwise.
- **Do not ask one clarifying question at a time across multiple turns.** Batch questions together.

## Session hygiene

- At the start of each session, confirm which task is being worked on and which files are in scope
- At the end of a task, explicitly state what was produced, where files were saved, and what the logical next step would be
- If a session ends mid-task, summarise the current state clearly so that the next session can resume with full context (remembering that Cowork starts fresh each session)
